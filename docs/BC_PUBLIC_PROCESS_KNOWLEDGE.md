# BC public process knowledge

The standard knowledge catalog includes Microsoft Learn process references and a small set of source-backed action rules. Rules identify observable UI actions or fields; they do not assert that a posting succeeded or that a business outcome occurred. Recordings remain the evidence for what a user did.

Sales and purchase order-line fields and actions, returns/corrections, cash/payment, documented warehouse pick/receipt/put-away actions, production-journal posting/output/consumption quantity, and selected project usage/journal actions include runtime-tested matches in all eight UI locales supported by BC Process Studio: `sv-SE`, `en-US`, `fr-FR`, `de-DE`, `es-ES`, `da-DK`, `fi-FI`, and `nb-NO`. Each rule retains source IDs, and action-resolution results include the cited source references. Other warehouse rules, inventory, service, and core-action rules still have narrower language coverage. Microsoft Learn labels and examples do not guarantee identical captions in every tenant, extension, or Business Central version.

## Process variants and limits

Business Central warehouse procedures depend on the location's setup. Microsoft's documentation describes order-line posting, inventory pick/put-away documents, warehouse shipment/receipt documents, and advanced flows that separate picking or receiving from shipment or put-away. The catalog therefore recognizes individual observed steps and leaves the process variant to the captured page sequence and labels. It does not impose a single universal order-to-cash or procure-to-pay path.

Likewise, posting an order can produce shipment and invoice documents together or independently, and partial quantities are supported. A recognized `Post` action means the user invoked a posting command; the recording must provide separate evidence before the process document reports success. Return orders and credit memos are distinct variants, and the catalog recognizes only documented commands and fields. Direct cancel/correct actions on posted invoices have documented eligibility limits (including unpaid status); matching their labels does not assert that the invoice met those conditions. The return-order flow is the documented alternative when item-level return handling is needed. Likewise, posting a payment journal records the payment in Business Central; the external bank transfer is a separate step. Payment-reconciliation suggestions must be reviewed before posting, and the catalog records the commands without treating a match suggestion as a confirmed payment.

## Updating the catalog

Add official Microsoft Learn references to `sources` in the relevant pack, record access date and scope, and attach source IDs to each sourced rule. Validate source IDs with `npm run knowledge:validate`; run `node tests/knowledge-catalog.test.js` after changes to action resolution. Avoid adding action captions based only on guesswork: rules should be constrained by the page and by the field or command documented in the source.
