# BC public process knowledge

The standard knowledge catalog includes Microsoft Learn process references and a small set of source-backed action rules. Rules identify observable UI actions or fields; they do not assert that a posting succeeded or that a business outcome occurred. Recordings remain the evidence for what a user did.

## Process variants and limits

Business Central warehouse procedures depend on the location's setup. Microsoft's documentation describes order-line posting, inventory pick/put-away documents, warehouse shipment/receipt documents, and advanced flows that separate picking or receiving from shipment or put-away. The catalog therefore recognizes individual observed steps and leaves the process variant to the captured page sequence and labels. It does not impose a single universal order-to-cash or procure-to-pay path. Combining sales shipments requires posted shipments that are not yet invoiced for the same customer and currency. The purchase-invoice Get Order Lines action has documented exclusions, including project-linked orders, prepayments, item charges, subcontracting, blanket orders, and intercompany transactions; automatic receipt also has warehouse and partial-receipt constraints.

Inventory availability views distinguish posted on-hand quantity from projected available balance, which adds scheduled receipts and subtracts gross requirements. Location-level availability requires inventory at more than one location, and warehouse pick availability can also depend on bin allocations and reservations. BOM-level availability is useful for checking component constraints and possible assembly/production quantities; it is not evidence that an order was released, materials were reserved, or production succeeded. The localized standard availability article documents views by event, period, location, BOM level, unit of measure and variant, but the catalog only matches UI captions that were verified in localized documentation. Unit-of-measure availability therefore remains a documented source topic, not a runtime action rule yet.

For production orders, Replan handles component/routing changes and can include lower BOM levels, while Refresh recalculates order lines from the header. Refresh can delete and recreate existing production-order lines and component recalculation can discard previous component edits, so an action match must be reviewed in context before the process guide recommends it. Likewise, posting an order can produce shipment and invoice documents together or independently, and partial quantities are supported. A recognized `Post` action means the user invoked a posting command; the recording must provide separate evidence before the process document reports success. Return orders and credit memos are distinct variants, and the catalog recognizes only documented commands and fields. Direct cancel/correct actions on posted invoices have documented eligibility limits (including unpaid status); matching their labels does not assert that the invoice met those conditions. The return-order flow is the documented alternative when item-level return handling is needed. Likewise, posting a payment journal records the payment in Business Central; the external bank transfer is a separate step. Payment-reconciliation suggestions must be reviewed before posting, and the catalog records the commands without treating a match suggestion as a confirmed payment.
